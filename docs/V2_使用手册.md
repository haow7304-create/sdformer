# SDformer V2 数据处理、模型训练与预测服务使用手册

## 1. 版本说明

本版本面向以下三个事件数据集：

- 俄乌冲突
- 美伊战争
- 中日外交

系统从每个事件的原始 JSON 时序数据中构造统一训练数据，训练三套独立的 SDformer 模型，并通过 HTTP 接口返回指定时间点之前的历史真实数据和之后 48 小时的数据。

V2 版本的主要变化如下：

- 原始数据仍包含 48 个业务指标。
- 41 个适合连续时序回归的指标参与模型训练和预测。
- 7 个文本、类别、ID、时间或离散阶段指标不参与训练。
- 41 个预测指标展开后形成 309 个业务变量。
- 为 11 个分布指标增加 11 个内部有效性变量，因此模型通道数为 320。
- 数量指标使用 `log1p` 变换，缓解不同数量级和长尾峰值对训练的影响。
- 分布指标统一为 0～1 比例，并保证输出分量和为 0 或 1。
- 使用分组损失，避免字段较多的指标在训练时获得不合理的高权重。
- 使用验证集校准模型预测和持久性基线，降低不稳定预测带来的退化。
- “舆情传播阶段”不再作为连续值预测，而是从原始 JSON 获取真实值。

## 3. 指标划分

### 3.1 模型预测指标

模型预测 41 个业务指标。包含字典结构的指标会按子项展开，因此 41 个指标最终对应 309 个业务变量。

指标类型分为：

- `distribution`：分布指标，例如地域、年龄、性别、情绪分布。
- `count`：数量指标，例如潜在受众数量、传播者数量、平台响应用户数量。
- `bounded_index`：理论范围为 0～1 的指数。
- `unbounded_index`：不强制限定为 0～1 的普通数值指数。

完整指标到变量列的映射保存在：

```text
dataset/processed_v2/feature_schema.json
```

### 3.2 不参与模型训练的 7 个指标

以下指标不会被转换为训练通道，也不会使用模型预测：

| 指标 | 排除原因 |
|---|---|
| 最具影响力用户 | 用户 ID 列表，不具备连续数值含义 |
| 最具正能量用户 | 用户 ID 列表 |
| 最具负能量用户 | 用户 ID 列表 |
| 相关热搜关键词 | 文本关键词列表 |
| 最具热度平台 | 平台类别，且原始结构可能不一致 |
| 平台首次响应时间 | 字符串日期，不适合作为连续回归目标 |
| 舆情传播阶段 | 离散阶段变量，不适合作为连续回归目标 |

历史和未来结果中仍然包含这 7 个指标，其值直接来自原始 JSON。

### 3.3 309 与 320 的关系

```text
41 个可预测业务指标
        ↓ 展开字典子项
309 个业务变量
        +
11 个分布有效性辅助变量
        ↓
320 个模型内部变量
```

11 个有效性变量只用于模型训练、校准和分布后处理，不作为独立业务指标返回前端。

因此配置必须为：

```text
enc_in = 320
dec_in = 320
c_out  = 320
```

接口元数据会同时返回：

- `business_variable_count: 309`
- `model_internal_variable_count: 320`

## 4. 数据处理逻辑

处理脚本为：

```text
dataset/process_json_time_series.py
```

### 4.1 建立统一字段结构

脚本会先扫描三个 JSON 文件，共同建立一份字段结构，确保三个数据集：

- 指标集合一致；
- 字典子项集合一致；
- CSV 列名一致；
- CSV 列顺序一致；
- 模型输入维度均为 320。

情绪类别中的“中性”和“中立”会统一为“中立”。

### 4.2 分布指标

用户属性类分布在原始数据中可能使用百分数或带 `%` 的字符串，处理时统一除以 100，转换为 0～1 比例。

对全部 11 个分布指标执行：

1. 将每个分量解析为有限数值，并在元数据中记录分量和检查结果。
2. 当所有分量之和大于 0 时，归一化为分量和等于 1，并设置 `valid=1`。
3. 当所有分量之和为 0 时，所有分量保持 0，并设置 `valid=0`。
4. 为每个分布增加一个内部有效性变量。

训练损失会惩罚模型产生的负分量；接口后处理还会把预测分量限制为非负并重新归一化。

### 4.3 数量指标

数量指标在写入训练 CSV 前执行：

```text
x_train = log(1 + x_raw)
```

推理返回前执行：

```text
x_public = round(max(exp(x_pred) - 1, 0))
```

这样能够压缩长尾数量级，并确保接口返回非负整数。

### 4.4 指数指标

- 有界指数在接口输出时限制到 0～1。
- 无界指数保持普通有限浮点数。
- 模型产生的非有限值会被视为运行错误，不会静默返回给前端。

### 4.5 时间和缺失数据

- 时间字段统一为 `YYYY-MM-DD HH:MM:SS`。
- 数据必须按小时连续。
- 重复时间戳默认使用数值均值合并。
- 包含任一保留变量缺失值的记录会被删除。
- 删除后如果出现非小时连续间隔，脚本会终止并报告错误。

### 4.6 目标列

热度指数在 CSV 中改名为 `OT` 并移动到最后一列。多变量预测仍会预测全部 320 个内部变量，`OT` 主要用于兼容项目现有的自定义数据加载器。

### 4.7 处理输出

每个事件生成：

- `<事件>.csv`：训练数据；
- `<事件>.preprocessor.json`：列顺序、缩放参数、常数列、变换规则；
- `<事件>.meta.json`：行数、时间范围、重复记录和分布检查结果。

同时生成公共的 `feature_schema.json`。

## 6. 模型训练

### 6.1 默认模型配置

| 参数 | 值 |
|---|---:|
| 模型 | SDformer |
| 输入长度 | 96 小时 |
| 预测长度 | 48 小时 |
| 输入/输出通道 | 320 |
| Encoder 层数 | 4 |
| `d_model` | 128 |
| `d_ff` | 128 |
| Batch size | 8 |
| Learning rate | 0.001 |
| 最大 Epoch | 20 |
| Early stopping patience | 4 |

### 6.2 GPU 配置

训练脚本通过 `PHYSICAL_GPU` 指定 `nvidia-smi` 中显示的物理 GPU 编号。

例如指定物理 GPU 7：

```bash
PHYSICAL_GPU=7 \
  bash scripts/custom_data/train_events_v2.sh
```

设置 `CUDA_VISIBLE_DEVICES=7` 后，程序内部看到的是 `cuda:0`，这是正常现象。

如需指定 Python 环境：

```bash
PHYSICAL_GPU=7 \
PYTHON_BIN=/home/liangjing/miniconda3/envs/llm/bin/python \
  bash scripts/custom_data/train_events_v2.sh
```

脚本会依次训练三个事件，避免同时加载多套训练任务造成显存压力。

### 6.3 分组损失

V2 使用 `GroupedForecastLoss`，主要逻辑为：

- 先在标准化空间计算误差；
- 每个业务指标获得相近权重，而不是每个展开字段获得相同权重；
- 分布误差只在真实分布有效时参与计算；
- 对分布负值和分量和偏离 1 增加约束惩罚；
- 单独学习 11 个分布有效性变量；
- 事件内恒定字段不参与不必要的分组预测损失。

## 7. 校准和质量评估

### 7.1 生成校准参数

训练结束后运行：

```bash
CUDA_VISIBLE_DEVICES=7 \
  /home/liangjing/miniconda3/envs/llm/bin/python \
  scripts/calibrate_v2.py
```

校准只使用验证集：

1. 按时间顺序将验证集分为拟合区和留出区。
2. 对每个指标、每个预测步拟合模型预测与持久性基线之间的混合系数。
3. 混合系数限制在 0～1。
4. 只有在验证留出区至少改善 0.5% 时才接受该指标的校准结果。
5. 未通过门控时使用持久性基线，即保持预测起点时的最后真实值。

校准文件保存在：

```text
new_checkpoints_v2/<event_key>/calibration.json
```

因此接口返回的是经过约束和校准的模型结果，不是未经处理的网络原始输出。

## 8. 后端接口逻辑

后端入口：

```text
forecast_api.py
```

请求包含：

- `p`：事件名称或事件 key；
- `t`：预测基准时间，必须是整点；
- `w`：历史窗口小时数，范围为 1～720。

### 8.1 历史范围

历史数据包含 `t` 时刻，共返回 `w` 个点：

```text
[t - (w - 1)小时, ..., t]
```

历史部分的 48 个指标全部来自原始 JSON。参与预测的数值指标会转换成与未来预测一致的公共单位，例如百分数分布会转换为 0～1 比例；7 个排除指标保持原始值。

### 8.2 模型输入

模型固定读取截至 `t` 的 96 小时数据：

```text
[t - 95小时, ..., t]
```

`w` 只控制返回给前端的历史长度，不改变模型的 96 小时输入长度。

### 8.3 未来范围

未来数据固定返回 48 个点：

```text
[t + 1小时, ..., t + 48小时]
```

每个未来时间点包含：

- 41 个经过反变换、校准和约束的模型预测指标；
- 7 个从相同未来时间戳的原始 JSON 获取的真实指标。

### 8.4 重要使用边界

由于 7 个排除指标要求返回未来真实值，因此当前接口主要适用于历史回放、模型评估或原始数据已经覆盖未来 48 小时的场景。

如果 `t+1` 至 `t+48` 的原始 JSON 数据不存在，接口会返回错误，而不会伪造这 7 个字段。真正的实时预测场景需要另行选择以下策略之一：

- 7 个字段返回 `null`；
- 只返回 41 个预测指标；
- 为离散或文本字段设计独立模型。

## 12. 完整更新流程

当原始 JSON 数据更新或处理规则改变时，按以下顺序执行：

```text
更新三个原始 JSON
        ↓
运行 process_json_time_series.py
        ↓
检查 processed_v2 元数据和字段数
        ↓
运行 train_events_v2.sh 训练三套模型
        ↓
运行 calibrate_v2.py 生成校准文件
        ↓
运行 evaluate_v2.py 查看质量报告
        ↓
运行 test_forecast_api_v2.py 验证接口契约
        ↓
启动 forecast_api.py
```

数据结构发生变化后不能只替换 checkpoint。必须同步更新以下文件：

- `checkpoint.pth`
- `preprocessor.json`
- `calibration.json`
- `feature_schema.json`
- 对应的 `processed_v2/<事件>.csv`

## 13. 常见问题

### 13.1 提示模型输入维度不一致

确认训练和后端均使用 320：

```text
enc_in=320
dec_in=320
c_out=320
```

并确认加载的是 `new_checkpoints_v2`，而不是旧版 `new_checkpoints`。

### 13.2 指定了 GPU 7，日志却显示 cuda:0

这是 `CUDA_VISIBLE_DEVICES` 的正常映射。物理 GPU 7 被屏蔽后，在当前进程内部重新编号为 `cuda:0`。

### 13.3 提示未来原始 JSON 数据缺失

接口需要从原始 JSON 获取未来 48 小时的 7 个真实字段。请把 `t` 调整到原始数据覆盖范围内，或者为实时场景修改这 7 个字段的返回策略。

### 13.4 提示历史不足 96 小时

模型固定需要 96 小时输入。请求时间 `t` 至少应位于处理后数据的第 96 个时间点。

### 13.5 端口被占用

更换端口：

```bash
PHYSICAL_GPU=7 API_PORT=8001 \
  bash scripts/start_forecast_api.sh
```

### 13.6 显存不足

- 确认只使用一个 Uvicorn worker；
- 使用 `nvidia-smi` 检查目标 GPU；
- 更换 `PHYSICAL_GPU`；
- 避免训练和接口服务同时使用同一张 GPU。
